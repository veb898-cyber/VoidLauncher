## 1. Цель и границы

### Цель

Дать пользователю полноценный редактор скина Minecraft Java Edition внутри VoidLauncher: рисовать по текстуре 64×64, импортировать PNG с компьютера, видеть результат на 3D-модели, сохранять скин в аккаунт Microsoft и экспортировать PNG. Редактор должен ощущаться частью лаунчера, а не отдельным сайтом: те же темы, стекло, шрифты, анимации и русская локализация.

### Что входит в MVP

- Открытие редактора полноэкранным диалогом из карточки выбранного аккаунта на странице «Аккаунты»: Microsoft, offline или Ely.by.
- Загрузка текущей текстуры, которую уже показывает лаунчер, либо встроенного default-скина как основы для редактирования.
- Импорт PNG 64×64 с компьютера прямо в редактор, с заменой текущего черновика после подтверждения. Импорт не переносится на следующий этап.
- Пиксельное редактирование текстуры 64×64: карандаш, ластик, заливка, пипетка.
- Отдельные базовый и внешний слои, управление видимостью внешнего слоя.
- Живой 3D-просмотр с выбором модели `classic`/`slim`.
- Отмена/повтор действий и сброс изменений к исходной/импортированной текстуре.
- Загрузка готового PNG в аккаунт Microsoft и обновление превью без перезапуска лаунчера.
- Экспорт PNG в выбранное пользователем место; экспорт доступен и для offline/Ely.by.
- Понятные ошибки: нет сессии, Mojang отклонил файл, нет сети, неподдерживаемый формат, ошибка импорта.
- Сохранение несохранённых изменений при ошибке загрузки и при повторной попытке.

### Что не входит в MVP

- Редактирование скинов Bedrock и запись в `custom_skins`/skin packs.
- Загрузка скина на Ely.by: публичного API загрузки в текущем коде нет, страница аккаунтов уже ведёт на сайт Ely.by.
- Редактор плащей: официальный API позволяет только выбирать-owned плащ, но не рисовать произвольный.
- Галерея чужих скинов, шаблоны из интернета, импорт скинов по ссылке.
- 3D-покраска по поверхности модели в реальном времени. В MVP используется 2D-атлас с подсветкой областей и 3D-превью.
- Совместное редактирование и облачное хранение черновиков.
- Постоянное хранение черновиков между перезапусками и локальная библиотека сохранённых скинов. В MVP черновик живёт только в памяти открытого редактора, а экспорт — это разовый PNG-файл, а не библиотека.
- Полноценное редактирование и конвертация legacy-текстур 64×32. Импорт принимает только 64×64; 64×32 обрабатывается как ограниченный legacy-случай, описанный ниже.

### Критерии успеха MVP

1. Пользователь открывает полноэкранный диалог редактора из карточки выбранного аккаунта, видит текущий/стартовый скин, импортирует или рисует PNG 64×64 и может изменить несколько пикселей.
2. Изменения сразу видны на 3D-модели, без мигания и пересоздания сцены; переключаются `classic`/`slim`.
3. Для Microsoft после «Применить» скин появляется в игре и в аватарах лаунчера, без ожидания семидневного кэша.
4. Ошибка загрузки/импорта не теряет нарисованное: редактор остаётся открытым, показывает причину и позволяет повторить.
5. Экспорт даёт корректный PNG 64×64, который открывается в игре и сторонних редакторах.
6. Offline- и Ely.by-аккаунты позволяют локально редактировать, импортировать и экспортировать PNG, но не предлагают загрузку на сервер.
7. Постоянные черновики и библиотека скинов не создаются; закрытие с несохранёнными изменениями требует подтверждения.
8. Все новые строки есть в `en.ts` и `ru.ts`; русский текст обращается на «вы».

### 1.1. Поведение по типам аккаунтов

**Предлагаемое решение:**

| Аккаунт | Редактирование и импорт | 3D-превью | Экспорт PNG | Загрузка на сервер |
|---|---|---|---|---|
| Microsoft | Да, стартовая текстура — текущий скин или импорт 64×64 | Да | Да | Да, только при действующей сессии |
| Offline | Да, стартовая текстура — текущий/default скин или импорт 64×64 | Да | Да | Нет |
| Ely.by | Да, стартовая текстура — то, что уже показывает карточка, default или импорт 64×64 | Да | Да | Нет; только ссылка на сайт Ely.by |

- Для offline и Ely.by кнопка загрузки отсутствует или disabled с объяснением: «Загрузка доступна только для аккаунта Microsoft».
- Для Microsoft без действующей сессии редактирование и экспорт остаются доступны; загрузка требует повторного входа, а черновик не теряется.
- Для Ely.by лаунчер не притворяется, что умеет загружать скин: пользователь может сохранить PNG и загрузить его на сайте Ely.by самостоятельно.
- Ни для одного типа аккаунта нет постоянного хранения черновика или библиотеки скинов в MVP.

## 2. Текущее состояние

### 2.1. Аккаунты и скины

**Подтверждено кодом:**

- `src/pages/Accounts.tsx` — страница управления аккаунтами. Выбранный аккаунт показывается большим `SkinPreview`; для Microsoft есть кнопка смены скина, для Ely.by — справка со ссылкой на сайт.
- `src/components/accounts/SkinPreview.tsx` — существующий 3D-просмотр:
  - размер по умолчанию 480×640, `HINT_RESERVE = 26`;
  - `skinview3d` загружается лениво;
  - viewer создаётся один раз, затем `loadSkin` меняет текстуру на месте;
  - модель задаётся как `auto-detect`;
  - плащ загружается отдельно через `loadCape`/`resetCape`;
  - данные скина приходят из `cmd_get_player_head` по UUID.
- `src/lib/skinHead.ts` — кроп головы из PNG; поддерживает 64×64 и 64×32; лицо `(8,8)`, overlay `(40,8)`.
- `src/stores/accountsStore.ts`:
  - `AccountEntry` содержит `id`, `name`, `account_type`, `uuid`, `skin_variant`, `default`, `has_ms_session`;
  - `changeSkin(accountId, skinPath, variant)` вызывает `cmd_change_skin`, затем перезагружает список аккаунтов;
  - кэш списка плащей — 45 секунд, список аккаунтов — короткий TTL с coalescing.
- `src-tauri/src/commands/auth.rs`:
  - `cmd_change_skin` принимает `account_id`, `skin_path`, `variant`;
  - проверяет существование файла и расширение PNG/JPG/JPEG;
  - для Microsoft получает сессию через `ensure_ms_session` и вызывает `change_microsoft_skin`;
  - сохраняет `skin_variant` в `accounts.json`;
  - `cmd_get_skin_path` ищет `data_dir/skins/<account_id>.png`, но frontend его не использует и такие файлы фактически не создаются.
- `src-tauri/src/auth.rs`:
  - `change_microsoft_skin` читает файл и отправляет multipart на `https://api.minecraftservices.com/minecraft/profile/skins`;
  - `variant` преобразуется в `SLIM` или `CLASSIC`;
  - токен берётся из серверной сессии, в renderer не передаётся.
- `src-tauri/src/commands/heads.rs`:
  - `cmd_get_player_head` возвращает **полный PNG скина** как data URL, несмотря на название;
  - кэш на диске — `data_dir/heads/<uuid>.png`, TTL 7 дней;
  - после смены скина старый файл кэша не инвалидируется автоматически.
- `src-tauri/src/default_skin.rs` — 18 встроенных vanilla-скинов; offline-аккаунты получают детерминированный default по UUID.

**Вывод:** загрузка скина уже есть, но это «выбрать файл и загрузить». Локального редактора, истории, слоёв и инвалидирования кэша после загрузки нет.

### 2.2. 3D-просмотр

**Подтверждено кодом:**

- `skinview3d` 3.4.2 установлен; `SkinViewer.loadSkin(source, { model })` принимает data URL и модель.
- `SkinLoadOptions.model` принимает `"default"`, `"slim"` или `"auto-detect"`; в коде лаунчера используется `auto-detect`.
- Viewer инициализируется с `IdleAnimation`, `autoRotate = false`, `controls.enablePan = false`.
- `SkinPreview` не принимает готовую текстуру извне: он всегда сам запрашивает её по UUID.

**Предлагаемое решение:** добавить в `SkinPreview` контролируемый режим — необязательные `skinOverride`, `model` и `interactive`. Если `skinOverride` задан, компонент не ходит в `cmd_get_player_head`, а загружает переданный data URL. Это позволит редактору использовать тот же проверенный viewer. Если изменение существующего компонента окажется рискованным, вынести общий `SkinViewerCanvas`/`useSkinViewer` и использовать его в обоих местах.

### 2.3. Файлы и безопасность

**Подтверждено кодом:**

- `src-tauri/src/download.rs` уже применяет атомарную запись: временный `.part`, проверка размера/хеша, затем `rename`.
- `src-tauri/src/commands/misc.rs` канонизирует пути и не выпускает операции за пределы `instances_dir`.
- `src-tauri/capabilities/default.json` разрешает `dialog:default`, `fs:default`, `opener:default`, `shell:default`; fs scope — `$APPDATA/**`, `$RESOURCE/**`.
- CSP разрешает `data:`/`blob:` изображения и `asset.localhost`.

**Предлагаемое решение:** не давать renderer произвольные пути для записи. Для загрузки скина backend сам создаёт временный файл в управляемой директории. Для экспорта путь приходит из системного диалога сохранения, но backend проверяет расширение `.png`, размер, сигнатуру PNG и пишет атомарно.

### 2.4. Локализация и UI-конвенции

**Подтверждено кодом:**

- `src/lib/i18n/en.ts` —source of truth, `ru.ts` повторяет структуру; `useT()`/`t()`.
- В UI используются `Modal`, `Button`, `Tooltip`, `Toast`, `LoadingSpinner`, `ConfirmDialog`; анимации 150–250 мс.
- Окно минимум 900×600; редактор должен помещаться без горизонтального скролла.

## 3. Предлагаемая архитектура

### 3.1. Точка входа

**Решение:** не добавлять отдельный пункт в Sidebar. Редактор — контекстное действие аккаунта:

- на странице «Аккаунты» рядом с существующей кнопкой смены скина добавить «Редактировать скин»;
- для Microsoft-аккаунта открывается полноэкранный диалог редактора с доступной загрузкой на сервер;
- для offline/Ely.by открывается тот же редактор с локальным редактированием, импортом и экспортом, но без загрузки на сервер;
- при закрытии с несохранёнными изменениями — подтверждение.

**Решение зафиксировано:** используется полноэкранный диалог, отдельная страница в MVP не создаётся. Редактор всегда привязан к конкретному аккаунту и его текущему скину; отдельный маршрут потребовал бы передачи контекста и добавил бы лишний пункт навигации.

### 3.2. Компоненты

```
src/components/skins/
  SkinEditorDialog.tsx      // полноэкранный диалог, загрузка исходника, действия
  SkinEditorToolbar.tsx     // инструменты, цвет, отмена/повтор, слои
  SkinEditorCanvas.tsx      // 2D-атлас 64×64, сетка, зум, рисование
  SkinEditorPreview.tsx     // 3D-превью (или контролируемый SkinPreview)
  SkinEditorPalette.tsx     // текущий цвет, alpha, недавние цвета
  skinEditorStore.ts        // состояние редактора и история
src/lib/skins/
  skinTexture.ts            // размеры, PNG, композит, UV-области
  skinHistory.ts            // снимки, undo/redo
  skinValidation.ts         // проверки перед загрузкой/экспортом
```

**Предлагаемое решение по состоянию:** zustand-стор с явными действиями (`beginStroke`, `paintPixel`, `endStroke`, `undo`, `redo`, `setLayer`, `setModel`, `reset`, `markSaved`). Пиксели хранить в `Uint8ClampedArray`/`ImageData`, а не в React-состоянии на каждый пиксель. Canvas рисуется императивно через `requestAnimationFrame`; React отвечает за панели и статусы.

### 3.3. Модель данных

```ts
type SkinLayer = 'base' | 'outer';

interface SkinDraft {
  width: 64;
  height: 64;
  base: Uint8ClampedArray;    // RGBA, 64×64
  outer: Uint8ClampedArray;   // RGBA, 64×64, прозрачный по умолчанию
  model: 'classic' | 'slim';
  dirty: boolean;
}
```

**Почему два буфера:** в PNG скина базовый и внешний слой лежат в разных UV-областях одной текстуры. Если хранить один буфер, ластик на внешнем слое может стереть базовый. Два буфера дают предсказуемое редактирование; при экспорте они собираются в один PNG.

**UV-карта.** Нужна таблица областей тела (голова, тело, руки, ноги; базовый/внешний слой). Точные координаты и различия slim-модели должны быть взяты из проверенного источника (`skinview-utils`/`skinview3d`) и покрыты тестами. **Требует исследования:** не изобретать координаты вручную; проверить на эталонных скинах classic и slim.

### 3.4. 2D-редактор

**Предлагаемое решение:**

- Холст показывает весь атлас 64×64 с шахматным фоном для прозрачности.
- Масштаб по умолчанию 8× (512×512 CSS-пикселей), диапазон 4×–16×; зум колесом с Ctrl, панорамирование средней кнопкой/пробелом.
- Сетка пикселей включается при масштабе ≥ 8×; линии не должны «съедать» пиксели.
- Подсветка областей тела и подписи (голова, тело, правая рука и т.д.) — опционально, чтобы не перегружать атлас.
- `imageSmoothingEnabled = false`; координаты через `Math.floor`, без сглаживания.
- Рисование через pointer events + `setPointerCapture`; один снимок истории на штрих, а не на пиксель.

**Инструменты MVP:**

| Инструмент | Поведение |
|---|---|
| Карандаш | 1 px, выбранный цвет и alpha; протяжка рисует линию без пропусков |
| Ластик | Устанавливает alpha = 0 в активном слое |
| Заливка | 4-связная flood fill по точному цвету; не выходит за активный слой |
| Пипетка | Берёт цвет из композита; показывает HEX/RGBA; не меняет данные |

**Инструменты следующего этапа:** прямая линия, прямоугольник, зеркальная кисть в пределах UV-грани, замена цвета, шаблоны, импорт палитры.

**Важно:** не делать «умное» сглаживание или антиалиасинг. Скин — пиксель-арт; любой blur испортит текстуру.

### 3.5. Импорт PNG 64×64

**Предлагаемое решение:**

- Кнопка «Импорт PNG» доступна в тулбаре редактора и в пустом состоянии.
- Файл выбирается через `<input type="file" accept="image/png">` и читается в renderer через `FileReader`/`createImageBitmap`; произвольный путь из файловой системы в backend не передаётся.
- Проверки до замены черновика: PNG-сигнатура, IHDR 64×64, отсутствие интерлейса, лимит размера (например, ≤ 512 КБ), успешное декодирование в 8-битный RGBA. Обычные цветовые типы PNG (RGB, RGBA, палитра) нормализуются в RGBA, чтобы редактор и загрузка работали с предсказуемым форматом.
- PNG разбирается на два буфера: базовый и внешний слой. Если внешний слой полностью прозрачный, это нормально.
- Модель из PNG не определяется: начальное значение берётся из `skin_variant` аккаунта, пользователь может переключить `classic`/`slim`; при загрузке передаётся выбранная модель.
- Если в редакторе есть несохранённые изменения, импорт сначала спрашивает подтверждение замены.
- При любой ошибке импорта текущий черновик остаётся нетронутым; показывается причина.
- Импортированный PNG можно редактировать и экспортировать; загрузка на сервер доступна только для Microsoft-аккаунта.
- 64×32 не импортируется и не конвертируется в MVP. Редактор показывает сообщение о legacy-формате и предлагает импортировать PNG 64×64; полноценная поддержка 64×32 — следующий этап.
- Импорт не создаёт запись в локальной библиотеке и не сохраняет файл в `data_dir`: это разовая замена текущего черновика.

**Почему импорт в MVP:** без него пользователь не может начать с готового скина, а редактор остаётся полезным только для правки текущего скина. Импорт PNG 64×64 не требует нового серверного API и не расширяет юридические границы.

### 3.6. Слои и модель

- Переключатель активного слоя: «Базовый» / «Внешний».
- Переключатель видимости внешнего слоя влияет только на превью и экспорт; данные не уничтожаются.
- Переключатель модели `classic`/`slim` меняет только 3D-модель; текстура остаётся той же.
- **Требует исследования:** как именно Mojang интерпретирует slim-развёртку и какие пиксели рук считаются значимыми; проверить на эталонном slim-скине.
- 64×32 не является полноценным режимом MVP: редактор не растягивает такую текстуру вслепую и не конвертирует её. Пользователь получает сообщение о legacy-формате и предложение импортировать PNG 64×64. Конвертация 64×32 → 64×64 — отдельный этап с тестами.

### 3.7. 3D-превью

**Предлагаемое решение:**

- Использовать существующий `skinview3d`; не добавлять второй 3D-движок.
- Обновлять текстуру через `loadSkin(dataUrl, { model: 'default' | 'slim' })` с debounce 80–120 мс.
- Не пересоздавать viewer при каждом штрихе; камера и анимация должны сохраняться.
- Показывать спереди; дать пользователю вращать модель, но не включать auto-rotate.
- Для внешнего слоя: при выключенной видимости компоновать preview-текстуру с alpha = 0 в outer-областях, не меняя draft.
- Плащ в редакторе не обязателен; если показывать, только активный плащ аккаунта и без редактирования.

### 3.8. Загрузка в Microsoft

**Предлагаемое решение:** добавить backend-команду, а не переиспользовать путь к произвольному файлу из renderer.

```text
cmd_upload_skin_png(account_id, png_bytes, variant) -> PublicAccountEntry
```

Порядок:

1. Найти аккаунт по `account_id`; разрешить только `AccountType::Microsoft` с сохранённой сессией.
2. Проверить размер (например, ≤ 512 КБ), PNG-сигнатуру и IHDR: 64×64, 8-bit RGBA, без интерлейса. Редактор отправляет уже нормализованный RGBA, но backend повторно проверяет формат и не доверяет renderer.
3. Записать временный файл в управляемую директорию `data_dir/skins/` (имя только из проверенного account id; никаких `..`, слэшей и unicode-разделителей).
4. Вызвать существующий `change_microsoft_skin` с временным файлом и `CLASSIC`/`SLIM`.
5. При успехе: сохранить `skin_variant`, удалить/заменить временный файл, инвалидировать `data_dir/heads/<uuid>.png`.
6. Вернуть обновлённый публичный аккаунт; frontend обновляет store и превью.
7. При ошибке: удалить временный файл, вернуть человекочитаемую ошибку, не менять аккаунт.

**Почему нужна отдельная команда:** текущий `cmd_change_skin` доверяет пути из renderer и не проверяет PNG-содержимое. Для редактора важно, чтобы backend был последней линией защиты, даже если frontend скомпрометирован.

**Инвалидирование кэша обязательно.** Сейчас `cmd_get_player_head` считает диск-кэш свежим 7 дней. Без удаления `heads/<uuid>.png` пользователь после загрузки увидит старый скин. Нужен helper в `heads.rs`, например `invalidate_skin_cache(data_dir, uuid)`, и вызов после успешной загрузки.

### 3.9. Экспорт PNG

**Предлагаемое решение:**

- Кнопка «Экспорт PNG» открывает системный диалог сохранения (`tauri-plugin-dialog`).
- Backend получает выбранный путь, проверяет расширение `.png`, пишет атомарно (`.part` → `rename`), не перезаписывает без подтверждения.
- Имя по умолчанию: `<nickname>-skin.png` с безопасной очисткой.
- Экспорт доступен и для offline/Ely.by: это просто файл, без сетевой загрузки.
- Экспорт не создаёт запись в библиотеке, не копирует файл в `data_dir` и не меняет аккаунт. Это разовый пользовательский файл.

### 3.10. Черновики, локальные скины и защита от потери

**MVP:** черновик живёт только в памяти, пока открыт диалог. При закрытии с `dirty` показывается подтверждение «Выйти без сохранения?». При ошибке импорта или загрузки на сервер черновик остаётся в памяти и доступен для повторной попытки/экспорта.

**В MVP нет:**

- автосохранения черновика между перезапусками;
- постоянной библиотеки локальных скинов;
- файлов проекта с отдельными слоями;
- восстановления черновика после закрытия приложения.

**Следующий этап:** автосохранение черновика в `localStorage` по ключу `voidlauncher.skinDraft.<accountId>` с версией и лимитом размера и/или отдельная библиотека скинов. Это требует отдельного решения и не должно менять контракт загрузки на сервер. Не хранить в черновике токены и не смешивать его с `accounts.json`.

## 5. Ошибки и безопасность

### Пользовательские ошибки

- Нет Microsoft-сессии или сессия истекла → предложить войти заново, не терять draft.
- Mojang отклонил PNG → показать ответ без токенов и внутренних путей; предложить проверить прозрачность/размер.
- Сеть недоступна → сохранить draft, дать «Повторить».
- Файл слишком большой/не PNG/не 64×64 → отказ до замены draft; текущий рисунок остаётся.
- Неподдерживаемый аккаунт (offline/Ely.by) → редактор доступен, загрузка недоступна; объяснить, что Ely.by меняется на сайте.
- Старый формат 64×32 → сообщение о legacy-формате, отказ от редактирования/конвертации, предложение импортировать PNG 64×64; текущий draft не меняется.

### Техническая безопасность

- Не принимать произвольный `skin_path` из renderer для загрузки; backend сам создаёт временный файл.
- Валидировать account id как безопасный идентификатор перед использованием в пути.
- Ограничить размер PNG и распакованных данных; не доверять расширению файла.
- Не логировать содержимое PNG, токены, cookie и ответы авторизации.
- Не отправлять скин никуда, кроме официального `api.minecraftservices.com`.
- Атомарная запись и очистка временных файлов при ошибке.
- Не добавлять новые capabilities/разрешения без необходимости; экспорт — через диалог пользователя.

### Юридические границы

- Редактор работает с PNG, который создал пользователь; не встраивать чужие скины и не делать галерею без лицензии.
- Не обходить лицензию Minecraft и не автоматизировать вход в Microsoft-аккаунт.
- Не использовать логотипы/арт Mojang как оформление редактора без разрешения.

## 6. Тестирование

### Unit-тесты (frontend)

- `skinValidation`: 64×64 проходит; 64×32 отклоняется редактором; 128×128, пустой файл, JPEG-сигнатура отклоняются.
- `pngImport`: импорт 64×64 заменяет draft только после подтверждения; ошибка импорта не меняет текущие пиксели; 64×32 не конвертируется.
- `skinTexture`: композит base+outer, прозрачность outer, экспорт PNG-заголовка.
- `skinHistory`: undo/redo, лимит снимков, сброс redo после нового штриха.
- `floodFill`: 4-связность, границы, прозрачные пиксели, большой однотонный регион.
- `model`: `classic` → `default`, `slim` → `slim`.

### Backend-тесты

- Валидация PNG: сигнатура, IHDR, размеры, RGBA, интерлейс, максимальный размер.
- Санитизация account id и временного пути.
- Инвалидирование кэша: после вызова файл `heads/<uuid>.png` отсутствует.
- Ошибка upload не меняет `skin_variant` и не оставляет `.part`.
- Не-Microsoft аккаунт получает понятный отказ.

### Интеграционные и ручные проверки

- Открыть редактор для Microsoft-аккаунта, изменить пиксель, применить, увидеть новый скин в `SkinPreview` и на странице «Аккаунты».
- Импортировать PNG 64×64 с компьютера, отредактировать и экспортировать; проверить, что 64×32 отклоняется с понятным сообщением.
- Проверить classic и slim.
- Проверить отмену/повтор после 20+ штрихов.
- Проверить закрытие с несохранёнными изменениями.
- Проверить экспорт и повторный импорт PNG в игру.
- Проверить offline и Ely.by: локальное редактирование/импорт/экспорт, отсутствие загрузки на сервер.

## 7. Критерии готовности

- Все пункты MVP выполнены и проверены на реальном Microsoft-аккаунте с согласия владельца.
- Импорт PNG 64×64 и экспорт PNG работают; 64×32 не конвертируется.
- Offline/Ely.by позволяют локальное редактирование, импорт и экспорт, но не загрузку на сервер.
- Постоянные черновики и локальная библиотека скинов не создаются.
- Нет регрессий в существующей смене скина через файл.
- После загрузки обновляются все аватары, а не только большой preview.
- Ошибка не приводит к потере draft и не оставляет мусорных файлов.
- Новые строки локализованы; русский текст на «вы».
- Анимации плавные, без резких скачков; reduced motion учитывается.
- `tsc`, `vitest`, `cargo fmt`, `cargo clippy`, `cargo test` зелёные.
- Документация обновлена, если фактическая архитектура отличается от плана.

## 8. Риски

| Риск | Влияние | Смягчение |
|---|---|---|
| Неверная UV-карта или slim-развёртка | Рисунок попадает не туда | Эталонные скины, сравнение с `skinview3d`, тесты |
| Mojang отклоняет PNG из-за alpha/формата | Загрузка не работает | Spike, серверная валидация, предупреждения |
| Старый кэш голов 7 дней | Пользователь не видит новый скин | Инвалидировать `heads/<uuid>.png` после успеха |
| Большая история | Рост памяти | Снимки 16 КБ, лимит 50, освобождение при закрытии |
| Случайная потеря рисунка | Недовольство | Подтверждение выхода, сохранение draft при ошибках; автосохранение — только следующий этап |
| Импорт повреждённого PNG | Потеря текущего рисунка | Валидация до замены, подтверждение, draft не меняется при ошибке |
| Смешение с Bedrock-скинами | Путаница | Четко разделить Java и Bedrock в UI и документации |
| 64×32 скины | Нельзя редактировать | Сообщение о legacy-формате, конвертация только на следующем этапе |
| Ely.by без API | Нельзя загрузить из лаунчера | Оставить ссылку на сайт, не имитировать загрузку |

## 9. Сложность и оценка

- **MVP:** M, примерно 5–7 рабочих дней при готовом spike.
- **Этап 2:** M, 3–5 дней.
- **Этап 3:** L, 5–10 дней и отдельное исследование 3D-покраски.
- **Основная сложность:** не canvas, а корректная UV-модель, slim-развёртка, валидация Mojang, импорт PNG и обновление кэшей без рассинхронизации.

## 1. Цель и границы

### Цель

Дать пользователю безопасный редактор **одной** собственной темы: выбрать встроенную тему как основу, изменить 15–25 ключевых цветов, увидеть результат на реальных компонентах, сохранить и применить тему, сбросить изменения к базовой теме и обменяться готовой темой через JSON-файл. Редактор не должен позволять произвольный CSS, ломать вёрстку или смешиваться с Liquid Glass.

### Что входит в MVP

- Одна пользовательская тема — без списка, библиотеки и управления несколькими темами.
- Выбор любой встроенной темы как основы: `standard`, `ember`, `dark`, `phosphor`, `carbon`, `blueprint`.
- Редактирование 22 ключевых цветовых токенов (в пределах требуемых 15–25): фон, поверхности, границы, текст, акценты, семантика.
- Живой предпросмотр на реальных классах интерфейса.
- Создание, сохранение и применение одной темы.
- Сброс пользовательских изменений к значениям выбранной базовой темы.
- Отключение темы без потери сохранённого варианта.
- Удаление сохранённой темы с подтверждением.
- Импорт и экспорт темы через JSON.
- Строгая валидация импортируемых данных.
- Проверка контраста основных пар цветов.
- Совместимость с Liquid Glass: режимы не смешиваются; после отключения Liquid Glass восстанавливается выбранная пользовательская тема.
- Сохранение после перезапуска без вспышки неправильной темы при старте.
- Локализация en/ru и существующие UI-конвенции.

### Что не входит в MVP

- Библиотека нескольких пользовательских тем, список, сортировка, поиск, избранное.
- Хранение до 20 тем, дублирование и удаление нескольких тем, переименование набора.
- Редактор всех 78 CSS-переменных, теней, градиентов, радиусов и прочих расширенных параметров.
- Светлые темы: текущий `applyAppearance` ставит `colorScheme = 'dark'`, а CSS рассчитан на тёмные темы.
- Пользовательские шрифты, фоновые изображения и обои для обычных тем.
- Тонировка Liquid Glass пользовательскими цветами.
- Произвольный CSS, загрузка `.css`-файлов.
- Обмен по ссылке, магазин тем, рейтинги, облачная синхронизация.
- Автоматическое применение импортированной темы без предпросмотра и подтверждения.

### Критерии успеха MVP

1. Пользователь создаёт одну тему на основе встроенной, меняет 5–10 цветов и видит читаемый предпросмотр.
2. После «Применить» весь лаунчер использует тему; перезапуск сохраняет результат.
3. Встроенные темы остаются неизменными; возврат к ним работает.
4. «Сбросить к базовой» возвращает все переопределённые токены к выбранной основе.
5. «Отключить мою тему» возвращает встроенную тему, не удаляя сохранённую пользовательскую.
6. Liquid Glass при включении полностью перекрывает пользовательскую тему, а при выключении возвращает её.
7. Импорт повреждённого или вредоносного JSON не ломает приложение и не применяет CSS.
8. Экспортированная тема импортируется на другой машине и выглядит так же.
9. Контраст основных текстов проверяется; критические сочетания не применяются молча.
10. В MVP нет списка и библиотеки нескольких тем — только один слот «Моя тема».

### 1.1. Поведение пользователя

**Предлагаемое решение:**

- В Settings остаётся существующий селект встроенных тем.
- Под ним появляется отдельная карточка «Моя тема»; она не смешивается со списком встроенных тем.
- Если темы нет: кнопки «Создать на основе текущей» и «Импорт».
- Если тема сохранена: миниатюра, кнопки «Изменить», «Применить», «Отключить», «Экспорт», «Удалить».
- «Создать» открывает редактор с базой, равной текущей встроенной теме.
- «Изменить» открывает сохранённую тему; изменения применяются только после «Сохранить и применить».
- «Сбросить к базовой» внутри редактора очищает все переопределения и показывает чистую базовую тему.
- «Отключить» не удаляет сохранённую тему; при повторном включении она снова применяется.
- «Удалить» удаляет сохранённый слот после подтверждения.
- Импорт заменяет текущий слот только после валидации и подтверждения; при ошибке текущая тема остаётся.

## 2. Текущее состояние

### 2.1. Управление темой

**Подтверждено кодом:**

- `src/stores/themeStore.ts`:
  - `Theme` — union из `standard`, `ember`, `dark`, `phosphor`, `carbon`, `blueprint`;
  - ключи localStorage: `voidlauncher-theme`, `voidlauncher-liquid-glass`;
  - Liquid Glass — отдельный sentinel `'lg'`, не входит в `Theme`;
  - `applyAppearance(theme, liquidGlass)` — единственный writer `data-theme`;
  - `data-lg-realistic="1"` ставится всегда;
  - `data-motion="liquid"` ставится на `<html>` при загрузке модуля;
  - `colorScheme` всегда `dark`;
  - при включённом Liquid Glass `setTheme` заблокирован, а выбранная обычная тема сохраняется для возврата.
- `src/pages/Settings.tsx`:
  - секция Appearance содержит язык, шрифт UI, шрифт консоли, выбор темы;
  - при Liquid Glass селект темы disabled;
  - ниже — экспериментальный блок Liquid Glass, обои и карточки контента.
- `index.html`:
  - inline bootstrap до React ставит `data-theme`, `data-motion`, `data-font`, `data-font-mono`, чтобы не было вспышки;
  - известные темы перечислены вручную; `standard` намеренно не ставится, остаётся дефолт из `:root`;
  - splash-фон задан отдельными правилами для `dark`, `ember`, `phosphor`, `carbon`, `lg`.
- `src/index.css`:
  - `:root` содержит 78 переменных;
  - блоки тем содержат примерно 45–54 переменные, Liquid Glass — 62;
  - 175 вхождений `data-theme`, 1027 `var(--...)`, 107 hex-цветов, 229 `rgba/rgb`, 135 `hsl/hsla`, 19 `!important`;
  - Liquid Glass scoped к `[data-theme='lg']`;
  - есть тематические селекторы, которые меняют не только переменные: фон main-content, тени, grid-паттерны, scrollbar, кнопки play и т.п.

**Вывод:** архитектура пресетов уже аккуратная: одна точка записи `data-theme`, Liquid Glass структурно отделён. Но пользовательской темы, редактора, импорта/экспорта и проверки контраста нет. Библиотека тем не нужна для MVP.

### 2.2. Где тема используется

**Подтверждено кодом:**

- `Settings.tsx` импортирует `Theme` и строит `themeLabel`.
- `LiquidGlassWallpaper`, `ContentManager`, `ScreenshotsGallery`, `ServersManager`, `WorldsManager`, `SlidingTabs` читают `useThemeStore`, в основном чтобы понять, включён ли Liquid Glass.
- `src/main.tsx` импортирует `themeStore` для применения темы до рендера.
- Другие страницы используют CSS-переменные и не должны знать о конкретной теме.

**Следствие:** расширение store нужно делать обратно совместимым. Нельзя заменять `theme: Theme` на объект без миграции всех потребителей. Нужно добавить один слот `customTheme` и флаг `customThemeEnabled`, оставив `theme` базовой встроенной темой.

## 3. Предлагаемая архитектура

### 3.1. Модель одной темы

**Предлагаемое решение:** пользовательская тема — версионированное JSON-описание переопределений над встроенной базой. Сохраняемые и экспортируемые данные отделены от вычисленного runtime-состояния.

```ts
type BuiltinTheme =
  | 'standard'
  | 'ember'
  | 'dark'
  | 'phosphor'
  | 'carbon'
  | 'blueprint';

type ThemeToken =
  | 'bg-primary'
  | 'bg-secondary'
  | 'bg-tertiary'
  | 'bg-elevated'
  | 'surface-glass'
  | 'surface-glass-hover'
  | 'surface-glass-active'
  | 'surface-active'
  | 'surface-border'
  | 'surface-border-hover'
  | 'text-primary'
  | 'text-secondary'
  | 'text-tertiary'
  | 'text-disabled'
  | 'primary'
  | 'secondary'
  | 'accent'
  | 'primary-contrast'
  | 'success'
  | 'warning'
  | 'error'
  | 'info';

type DerivedCssVar =
  | '--primary-dim'
  | '--primary-light'
  | '--accent-dim'
  | '--gradient-primary'
  | '--gradient-primary-hover'
  | '--glow-primary'
  | '--glow-primary-intense'
  | '--danger-bg'
  | '--danger-border'
  | '--danger-bg-hover'
  | '--banner-error-bg'
  | '--banner-error-border'
  | '--log-error-bg'
  | '--log-warn-bg'
  | '--slider-shadow'
  | '--slider-shadow-hover'
  | '--color-danger'
  | '--color-warning'
  | '--color-success'
  | '--color-info'
  | '--surface-secondary';

type SeedCssVar = `--${ThemeToken}`;
type AppliedCssVar = SeedCssVar | DerivedCssVar;

interface CustomTheme {
  schema: 1;
  base: BuiltinTheme;
  appearance: 'dark';         // MVP: только тёмные темы
  overrides: Partial<Record<ThemeToken, string>>;
}

interface ResolvedCustomTheme {
  source: CustomTheme;
  resolvedVars: Partial<Record<AppliedCssVar, string>>;
}
```

- `CustomTheme` — единственный формат для localStorage и JSON-экспорта. В нём нет `resolvedVars`, `id`, имени и других вычисляемых или презентационных полей.
- `ResolvedCustomTheme` создаётся в памяти функцией `resolveCustomTheme(source)`. Он никогда не читается из localStorage или импортируемого файла, не экспортируется и не считается доверенным. Runtime-кэш допустим только как оптимизация в памяти и не переживает перезапуск.
- `resolvedVars` содержит нормализованные seed-переопределения (фиксированное отображение `ThemeToken` → `--<token>`) и вычисленные производные. В нём нет неизменённых токенов базы.
- `overrides` содержит только ключи из 22 seed-токенов. Отсутствующий токен наследуется от `base`; копировать все 78 переменных в JSON нельзя.
- `schema` — строго `1`; `appearance` — строго `'dark'`; `base` — только из allowlist. Неизвестные версии и значения отклоняются.
- Неизвестные top-level поля и неизвестные ключи `overrides` отклоняют весь объект. Объект не сливается через `Object.assign`; прототипы и служебные ключи (`__proto__`, `constructor`, `prototype`) запрещены.
- Значения `overrides` нормализуются парсером в канонический вид при сохранении и экспорте; сырые строки не хранятся и не применяются.
- Пользователь не может передать CSS-правило, `url()`, `var()`, `calc()` или произвольную функцию. Даже производные строки — это только фиксированные шаблоны доверенного кода.

**Почему один объект, а не массив:**

- требование MVP — одна пользовательская тема, а не библиотека;
- нет id, имени, сортировки, дублирования, конфликтов импорта и удаления нескольких тем;
- меньше UI, меньше состояний и меньше риска рассинхронизации;
- при необходимости библиотека добавляется на следующем этапе без изменения формата `overrides`.

**Почему `base` + `overrides`, а не копия всех 78 переменных:**

- встроенные темы уже содержат ручные настройки, тени и паттерны; копировать их в JSON — значит дублировать CSS и ловить расхождения;
- пользователь меняет только выбранные 22 seed-токена; остальное наследуется от базы;
- `resolvedVars` не является кэшем темы: он вычисляется заново из `overrides` при применении и при bootstrap. Поэтому сохранённый JSON нельзя «подделать» вычисленными значениями.

**Почему `data-theme` остаётся базовой темой:**

- селекторы вроде `[data-theme="dark"] .console` продолжают работать;
- пользовательские переменные накладываются поверх через inline `style.setProperty`;
- `data-custom-theme="active"` — только метаданные для UI; по нему **не** строятся CSS-селекторы.

### 3.2. Расширение themeStore

**Предлагаемое решение:**

```ts
interface ThemeState {
  theme: BuiltinTheme;              // встроенная тема, когда custom выключена
  customTheme: CustomTheme | null;  // единственный сохранённый слот, только source
  customThemeEnabled: boolean;
  liquidGlass: boolean;

  setTheme: (theme: BuiltinTheme) => void;       // выключает custom, не удаляет его
  saveCustomTheme: (theme: CustomTheme) => void; // сохраняет и применяет
  setCustomThemeEnabled: (enabled: boolean) => void;
  removeCustomTheme: () => void;
  setLiquidGlass: (enabled: boolean) => void;
}
```

`applyAppearance` остаётся единственным writer `data-theme` и единственным местом, которое ставит или снимает CSS-переменные пользовательской темы. Он принимает `theme`, `liquidGlass`, `customTheme` и `customThemeEnabled`, а не произвольный набор стилей.

1. Если `liquidGlass` — ставит `data-theme="lg"`, убирает `data-custom-theme` и только те inline-свойства, которые записал сам (`appliedCustomVars`).
2. Иначе если `customThemeEnabled && customTheme` — валидирует `source`, вызывает `resolveCustomTheme(source)`, ставит `data-theme=customTheme.base`, `data-custom-theme="active"`, применяет только `resolvedVars` из закрытого allowlist и запоминает имена применённых свойств.
3. Иначе — ставит `data-theme=theme`, убирает `data-custom-theme` и ранее применённые inline-переменные.
4. Всегда сохраняет `colorScheme = 'dark'` и не трогает чужие inline-стили.

`appliedCustomVars` — runtime-множество имён свойств, которые поставил именно механизм темы. Очищать `documentElement.style` целиком или удалять свойства по префиксу нельзя: там могут быть другие inline-стили. Если `resolveCustomTheme` падает или `source` не проходит валидацию, применяется встроенная `theme`, inline-переменные снимаются, а ошибка показывается в UI; частично применять тему запрещено.

`saveCustomTheme` сохраняет только normalized `source` без `resolvedVars` и синхронизирует `theme` с `customTheme.base` после успешной валидации. `setTheme` выключает custom, но не удаляет сохранённый слот. `setCustomThemeEnabled` меняет только флаг и вызывает `applyAppearance`; `removeCustomTheme` очищает слот и применяет встроенную тему.

**Совместимость:** `theme` остаётся `BuiltinTheme`; существующие компоненты, читающие store ради Liquid Glass, не меняются. `Settings.tsx` получает отдельную карточку «Моя тема», а не переделку селекта в список объектов.

### 3.3. Токены, значения и вычисление

**A. Пользовательские seed-токены (ровно 22).**

Все значения проходят через один и тот же `themeColor.parse`, независимо от источника: поле редактора, импорт или восстановление из localStorage. Строка не попадает в CSS до успешного разбора и нормализации.

Допустимые форматы:

- HEX: `#RGB`, `#RGBA`, `#RRGGBB`, `#RRGGBBAA` (регистр не важен);
- `rgb(R, G, B)` и `rgba(R, G, B, A)` только в legacy-синтаксисе с запятыми; `R/G/B` — целые `0..255`, `A` — число `0..1`.

Не принимаются: именованные цвета, `transparent`, `currentColor`, `hsl()/hsla()`, проценты в RGB, современный синтаксис с `/`, `calc()`, `color-mix()`, `var()`, `url()`, `env()`, `expression`, вложенные скобки, комментарии, точки с запятой и переводы строк. Строка длиннее 64 символов отклоняется до парсинга. HSL не входит в MVP: базовые HSL-значения остаются в CSS, но пользовательский ввод и JSON нормализуются в HEX/RGBA.

Правила alpha:

- `bg-primary`, `bg-secondary`, `bg-tertiary`, `bg-elevated` — только непрозрачные цвета (`alpha = 1`); это базовый слой для контраста.
- `surface-glass`, `surface-glass-hover`, `surface-glass-active`, `surface-active`, `surface-border`, `surface-border-hover` — alpha не обязательна, допустима `0..1`. Если alpha не указана, цвет считается непрозрачным. `alpha = 0` технически допустима, но UI предупреждает, что поверхность/граница станет невидимой.
- `text-*`, `primary`, `secondary`, `accent`, `primary-contrast`, `success`, `warning`, `error`, `info` — только непрозрачные цвета. `rgba(..., 1)` и `#RRGGBBAA` с alpha `1` принимаются и нормализуются в `#rrggbb`; alpha меньше `1` отклоняется.

Канонический результат: `#rrggbb` для непрозрачных значений и `rgba(r, g, b, a)` для значений с alpha меньше `1`; alpha округляется до трёх знаков. `overrides` хранит только канонические значения, без исходной строки пользователя.

Каждый seed применяется как `--<token>` по фиксированной таблице (`bg-primary` → `--bg-primary` и т.д.). Имена CSS-переменных не берутся из пользовательского ввода. `resolvedVars` содержит эти seed-значения и добавленные к ним производные из B.

**B. Производные переменные (закрытый allowlist MVP).**

Производные вычисляются только из изменённых seed-токенов. Если seed не переопределён, соответствующая производная не выводится и наследуется от базовой темы. Это сохраняет ручные настройки базы и не требует копировать 78 переменных.

| `--slider-shadow-hover` | `primary` | `primary` изменён | профиль из таблицы ниже |
| `--color-danger` | `error` | `error` изменён | `var(--error)` |
| `--color-warning` | `warning` | `warning` изменён | `var(--warning)` |
| `--color-success` | `success` | `success` изменён | `var(--success)` |
| `--color-info` | `info` | `info` изменён | `var(--info)` |
| `--surface-secondary` | `surface-glass` | `surface-glass` изменён | `var(--surface-glass)` |

`P`, `A`, `E`, `W` — уже разобранные RGB-компоненты `primary`, `accent`, `error`, `warning`. `var(--...)` в таблице — только фиксированные ссылки на разрешённые seed-токены, не пользовательский текст. `αbase` — профиль базы:

| База | `primary-dim` | `accent-dim` | `danger-bg` / `danger-border` / `danger-bg-hover` | `banner-error-bg` / `banner-error-border` | `log-error-bg` / `log-warn-bg` |
|---|---:|---:|---|---|---|
| `standard` | `0.10` | `0.15` | `0.15 / 0.20 / 0.25` | `0.10 / 0.25` | `0.06 / 0.06` |
| `dark` | `0.12` | `0.15` | `0.15 / 0.20 / 0.25` | `0.12 / 0.28` | `0.08 / 0.08` |
| `blueprint` | `0.10` | `0.12` | `0.08 / 0.22 / 0.14` | `0.08 / 0.22` | `0.06 / 0.06` |
| `ember` | `0.10` | `0.12` | `0.12 / 0.24 / 0.20` | `0.09 / 0.24` | `0.06 / 0.07` |
| `phosphor` | `0.10` | `0.13` | `0.12 / 0.24 / 0.20` | `0.10 / 0.26` | `0.07 / 0.07` |
| `carbon` | `0.10` | `0.12` | `0.12 / 0.24 / 0.20` | `0.10 / 0.26` | `0.07 / 0.07` |

Glow и slider используют только профиль своей базы:

| База | `glow-primary` | `glow-primary-intense` | `slider-shadow` / `slider-shadow-hover` |
|---|---|---|---|
| `standard` | `0 0 20px rgba(P, 0.30)` | `0 0 30px rgba(P, 0.50), 0 0 60px rgba(P, 0.20)` | `0 0 6px rgba(P, 0.40)` / `0 0 10px rgba(P, 0.60)` |
| `dark` | `0 0 20px rgba(P, 0.25)` | `0 0 30px rgba(P, 0.40), 0 0 60px rgba(P, 0.15)` | `0 0 6px rgba(P, 0.40)` / `0 0 10px rgba(P, 0.60)` |
| `blueprint` | не выводится — матовая база | не выводится — матовая база | `0 0 5px rgba(P, 0.25)` / `0 0 8px rgba(P, 0.40)` |
| `ember` | не выводится — матовая база | не выводится — матовая база | `0 0 6px rgba(P, 0.30)` / `0 0 10px rgba(P, 0.45)` |
| `phosphor` | `0 0 16px rgba(P, 0.16)` | `0 0 24px rgba(P, 0.24)` | `0 0 8px rgba(P, 0.28)` / `0 0 12px rgba(P, 0.42)` |
| `carbon` | не выводится — матовая база | не выводится — матовая база | `0 0 0 2px rgba(P, 0.12)` / `0 0 0 3px rgba(P, 0.20)` |

Для `blueprint`, `ember` и `carbon` переменные `--glow-primary` и `--glow-primary-intense` не вычисляются и наследуются от встроенной темы: сохраняются матовые тени базы, colored glow не генерируется, иначе тема потеряет свой характер. Для `standard`, `dark` и `phosphor` glow-переменные вычисляются по профилю; для `carbon` slider — это кольцо, а не размытие, шаблон сохраняется.

`--color-info` выводится только вместе с seed `--info`, а `--color-danger`/`--color-warning`/`--color-success` — только вместе со своими seed-токенами. Так алиасы не создают цикл с базовым правилом `--info: var(--color-info)` и не оставляют старый цвет.

**Не выводятся в MVP:** `--primary-dark`, `--glow-secondary`, `--glow-accent` — у них нет потребителей в текущих CSS/TSX, поэтому не добавляем их «на будущее». `--surface-elevated` остаётся алиасом `var(--bg-elevated)` и разрешается браузером автоматически. `--shadow-*`, типографика, радиусы, переходы и прочие переменные наследуются от базы.

**Точность формул:** `primary-light` с `+10` совпадает со `standard` и `dark`, но ручные значения `blueprint`, `ember`, `phosphor`, `carbon` могут отличаться. `gradient-primary` совпадает с простым шаблоном `standard`/`dark`/`blueprint`, тогда как `ember`, `phosphor`, `carbon` используют ручные литералы. `phosphor` glow и tints `danger`/`banner`/`log` — нормализованные производные, а не пиксельная копия ручных значений. Это осознанный контракт; перед релизом нужен визуальный аудит на всех шести базах. Если потребуется точное совпадение, расширять профили баз явными параметрами, а не встраивать произвольный CSS.

**C. Наследуемые значения.** Всё, что не входит в A или B, берётся из `:root` и блока `[data-theme=base]`: `--primary-dark`, `--glow-secondary`, `--glow-accent`, `--surface-elevated`, `--shadow-*`, типографика, отступы, радиусы, переходы, размеры sidebar/titlebar. Тематические селекторы (паттерны `.main-content`, scrollbar, splash и т.п.) и захардкоженные цвета вне переменных остаются базовыми и не управляются редактором. Закрытые allowlists A и B — единственный набор переменных, который применяет `applyAppearance`; редактор всех 78 переменных в MVP не появляется.

### 3.4. Предпросмотр

**Предлагаемое решение:** отдельный `ThemePreview` внутри редактора, а не мгновенное применение ко всему приложению.

- Контейнер получает `data-theme={base}` и `style={resolvedVars}`, где `resolvedVars` вычислен из текущего черновика тем же `resolveCustomTheme`, что и при применении. Storage и импортированные `resolvedVars` не используются.
- Невалидный черновик не меняет предпросмотр: последняя валидная версия остаётся на экране, ошибка показывается у поля.
- Внутри — реалистичная миниатюра: боковая панель, заголовок, две карточки, primary/secondary/danger кнопки, input, toggle, toast, прогресс-бар, строчка лога.
- Использовать настоящие классы (`glass-card`, `btn`, `input`, `toggle`, `toast`) и CSS-переменные, чтобы предпросмотр не расходился с продуктом.
- Показывать предупреждение о контрасте рядом с соответствующими полями.
- В MVP достаточно миниатюры; «примерка на всём лаунчере» с таймером — следующий этап.

**Почему не применять сразу:** пользователь может случайно сделать интерфейс нечитаемым; откат через `Ctrl+Z` для темы неочевиден. Применение по кнопке «Сохранить и применить» безопаснее.

### 3.6. Хранение одного слота

**Предлагаемое решение для MVP:** localStorage, потому что тема должна применяться до первого кадра, а `index.html` не может дождаться асинхронного Rust-вызова.

Ключи:

- `voidlauncher-custom-theme` — JSON одного `CustomTheme` без `resolvedVars`;
- `voidlauncher-custom-theme-enabled` — `'1'` или отсутствует;
- существующие `voidlauncher-theme` и `voidlauncher-liquid-glass` не ломать.

В localStorage лежит только source: `schema`, `base`, `appearance`, `overrides`. `resolvedVars` и список применённых свойств не сохраняются; после перезапуска они вычисляются заново. При загрузке source заново проходит валидацию и нормализацию; сырые значения из localStorage не применяются. Это исключает доверие к подделанному кэшу и гарантирует, что изменения CSS-профилей применяются к сохранённой теме.

Ограничения:

- один объект, не более 64 КБ; реальный лимит для 22 токенов значительно ниже;
- неизвестные поля, неизвестные ключи `overrides`, неверная версия схемы и неверный `base` считаются повреждёнными данными;
- при переполнении quota — понятная ошибка, тема остаётся в памяти и доступна для экспорта;
- повреждённый JSON не роняет приложение: показываем встроенную тему, не применяем частично прочитанные данные, предлагаем импортировать заново; слот автоматически не удаляем;
- `customThemeEnabled=true` при повреждённом слоте не применяет тему; эффективное состояние — встроенная `theme`, а UI показывает ошибку и кнопки восстановления;
- миграции схемы — только явные, с версией; в MVP поддерживается ровно `schema: 1`, неизвестные версии отклоняются;
- при `customThemeEnabled=false` сохранённый слот остаётся, но применяется встроенная `theme`.

**Почему не `config.json`:** синхронное чтение до первого paint невозможно без дополнительного bootstrap-кэша; localStorage уже используется для темы и подходит для раннего применения. **Риск:** очистка данных WebView удалит тему; поэтому экспорт в JSON обязателен. Библиотека и зеркало в app data — следующий этап.

### 3.7. Bootstrap до React

**Подтверждено кодом:** `index.html` уже содержит inline-скрипт, который применяет тему до первого кадра.

**Предлагаемое решение:**

- расширить скрипт: если `voidlauncher-custom-theme-enabled` включён, `voidlauncher-custom-theme` валиден и Liquid Glass выключен — поставить `data-theme=<base>`, `data-custom-theme="active"`, применить нормализованные seed-переопределения и **вычисленные заново** производные из закрытого allowlist;
- использовать те же правила, что и runtime: те же 22 ключа, тот же парсер hex/RGB/RGBA, те же alpha-ограничения, та же проверка `schema`/`base`/`appearance`, те же профили производных;
- никогда не читать `resolvedVars` из localStorage или JSON и не применять значения, которых нет в allowlist;
- если данных нет, они битые, слот отключён или `resolveCustomTheme` упал — не применять частично, оставить текущее поведение встроенной темы; ошибку показать после старта React;
- splash-фон перевести на `var(--bg-primary, <fallback для базы>)`, чтобы при смене `bg-primary` не было вспышки чужого цвета; декоративные градиенты splash не считать частью контракта темы;
- при активном Liquid Glass не применять custom-тему и не оставлять её inline-переменные;
- синхронизацию inline-скрипта и `themeStore` проверять тестом эквивалентности на всех шести базах и наборе overrides, плюс ручной проверкой первого кадра.

**Требует исследования:** можно ли вынести bootstrap в отдельный синхронный JS-файл, который импортирует общий валидатор, не ломая Vite/Tauri CSP. Пока это не подтверждено, нельзя обещать общий модуль: допускается компактный inline-скрипт с тем же контрактом и тестом эквивалентности. Ослаблять CSP, добавлять `unsafe-eval` или загружать валидатор с внешнего ресурса запрещено.

### 3.8. Импорт и экспорт

**Экспорт:**

- кнопка «Экспорт» → системный диалог сохранения (`tauri-plugin-dialog`);
- JSON строго из четырёх полей: `schema`, `base`, `appearance`, `overrides`; `resolvedVars`, `id`, имя и другие поля не экспортируются;
- значения `overrides` — только канонические HEX/RGBA после нормализации;
- backend/FS-запись только после выбора пути; проверять `.json`, размер и кодировку;
- имя файла: `voidlauncher-theme.json` с безопасной очисткой.

**Импорт:**

- скрытый `<input type="file" accept=".json,application/json">` + `FileReader` в renderer (не требует произвольного доступа к FS);
- лимит 128 КБ, глубина JSON не больше 3, не больше 22 ключей в `overrides`;
- top-level allowlist: ровно `schema`, `base`, `appearance`, `overrides`; любое дополнительное поле отклоняет файл;
- `schema` — строго `1`; `base` — из whitelist; `appearance` — строго `'dark'`; `overrides` — только 22 известных токена;
- значения проходят тот же парсер и те же alpha-ограничения, что и ручной ввод; ошибка в одном токене отклоняет весь файл;
- `resolvedVars` в файле запрещён и считается ошибкой, а не игнорируется: импорт не должен создавать впечатление, что вычисленные значения можно переносить;
- неизвестная версия схемы отклоняется без попытки угадать формат; миграций в MVP нет;
- валидация и предпросмотр выполняются до замены слота; при наличии сохранённой темы — подтверждение замены;
- замена слота и запись в localStorage происходят только после подтверждения и успешной валидации; при ошибке чтения/валидации/записи текущая тема и слот остаются прежними;
- после импорта показывается предпросмотр; применение — по кнопке «Применить»;
- CSS/JS-инъекция невозможна: импортированные строки никогда не попадают в `<style>`, `cssText`, `innerHTML` или шаблон CSS.

**Почему без id и списка:** одна тема — один слот; нет конфликтов идентификаторов, переименований и дубликатов.

### 3.9. Контраст и доступность

**Предлагаемое решение:**

- реализовать `relativeLuminance` и `contrastRatio` без внешних зависимостей;
- для полупрозрачных surface-токенов считать эффективный цвет композицией над `bg-primary`/`bg-secondary`; для текста брать эффективный фон, а не alpha-значение как непрозрачное;
- проверять как минимум:
  - `text-primary` на `bg-primary`;
  - `text-secondary` на `bg-primary`;
  - `text-primary` на `bg-secondary`;
  - `primary-contrast` на `primary`.
- дополнительно предупреждать о проблемах на `bg-elevated` и стеклянных поверхностях, где текст реально используется;
- порог: 4.5:1 для обычного текста, 3:1 для крупного/кнопок; для критических пар — предупреждение и требование подтверждения;
- `primary-contrast` не пересчитывается автоматически без действия пользователя, потому что это seed-токен; кнопка «Автоконтраст» подбирает чёрный/белый и предупреждает, если текст на фоне всё равно плох;
- `text-disabled` не обязан проходить 4.5:1, но должен оставаться отличимым от фона;
- не полагаться только на цвет: ошибки/успех дублируются иконкой/текстом (это уже в UI);
- фокус-кольца должны быть видны на всех кастомных темах; проверить keyboard navigation.

### 3.10. Взаимодействие с Liquid Glass

**Подтверждено кодом:** Liquid Glass — отдельный режим, а не тема; при нём `data-theme="lg"` и обычные темы заблокированы.

**Предлагаемое решение:**

- при включении Liquid Glass снять только `appliedCustomVars` и `data-custom-theme`; не очищать весь `documentElement.style`;
- при выключении — вычислить и восстановить сохранённую пользовательскую тему, если `customThemeEnabled=true`, иначе встроенную;
- если при включении LG тема была отключена или повреждена, после выключения применять встроенную `theme`, а не частично восстановленный custom;
- в Settings показывать карточку «Моя тема», но блокировать выбор, как сейчас для встроенных;
- не пытаться тонировать Liquid Glass пользовательскими цветами в MVP. Это отдельный этап, потому что стекло использует десятки собственных переменных и физику материала.

## 5. Ошибки и безопасность

### Пользовательские ошибки

- Некорректный цвет → подсветить поле, не менять preview.
- Alpha у непрозрачного токена → ошибка поля; для surface — допустима, при `0` показать предупреждение.
- Неизвестное поле/ключ, неверная схема или `base` → ошибка импорта, текущая тема не меняется.
- `resolvedVars` в импортируемом JSON → явная ошибка «вычисляемые значения не импортируются».
- Слишком низкий контраст → предупреждение, для критических пар — блокировка применения.
- Переполнение localStorage → предложить экспорт, не терять тему в памяти.
- Битый импорт → показать причину, не менять текущую тему.
- Импорт при существующей теме → подтверждение замены, старая тема остаётся до успешной валидации.
- Удаление темы → подтверждение; после удаления применяется встроенная.
- Отключение темы → сохранённый слот остаётся, применяется встроенная.

### Безопасность

- Никогда не вставлять пользовательские значения в `<style>`, `cssText`, `innerHTML`.
- Применять только закрытый allowlist CSS custom properties из раздела 3.3 через `style.setProperty`.
- Валидировать значения строгим парсером HEX/RGB/RGBA; запретить `;`, `}`, `{`, `url(`, `var(`, `calc(`, `color-mix(`, `@`, `expression`, `/*`, переводы строк, именованные цвета и `currentColor`.
- Производные строки генерировать только фиксированными шаблонами из доверенных RGB-компонентов; не конкатенировать пользовательский текст в CSS.
- `data-custom-theme` не использовать в CSS-селекторах; это только метка для UI.
- Импортируемый JSON считать недоверенным: лимит 128 КБ, глубины 3 и 22 ключей; проверять точный top-level allowlist, отклонять неизвестные поля и ключи; не использовать `Object.assign` и не позволять `__proto__`/`constructor`/`prototype`.
- Не принимать `resolvedVars` из импорта или localStorage как истину: пересчитывать их из `overrides`; в JSON и localStorage этого поля быть не должно.
- Не добавлять произвольные fs-разрешения; импорт через File API, экспорт через диалог.
- Не логировать содержимое темы и localStorage целиком.

### Производительность

- Применение темы — установка до 43 CSS-переменных на `<html>` (22 seed + не более 21 производной), обычно меньше; без React-ререндера.
- Preview не должен запускать тяжёлые анимации; использовать `prefers-reduced-motion`.
- Не хранить историю изменений темы в localStorage; только текущий слот.

## 6. Тестирование

### Unit-тесты (Vitest, текущая настройка проекта)

- `themeSchema`: валидная тема со всеми 22 токенами и частичная тема; пустой `overrides`; неизвестный top-level ключ; неизвестный токен; неверный `base`; неверный `appearance`; `schema: 2`; отсутствующий `schema`; `null`/массив/строка вместо объекта; `resolvedVars` в импорте; `__proto__`/`constructor`; превышение лимита ключей.
- `themeColor`: все HEX-формы, `rgb()`/`rgba()`, alpha `0`/`0.5`/`1`, округление до трёх знаков, канонический вывод; отказ для HSL, именованных цветов, `transparent`, `currentColor`, `var()`, `calc()`, `url()`, `;`, `}`, `{`, переводов строк, дробных/отрицательных RGB, alpha вне `0..1`.
- `themeSchema` alpha-политика: alpha запрещена для bg/text/акцентов/семантики; alpha разрешена для шести surface-токенов; alpha `0` у границы даёт предупреждение, но не ошибку парсера.
- `themeDerive`: каждый изменённый seed попадает в `resolvedVars` как `--<token>`; для каждого seed-токена — ровно ожидаемый набор производных; отсутствие производных при неизменённом seed; `primary` → dim/light/glow/slider/gradient; `secondary` → gradient; `accent` → accent-dim; `error` → danger/banner/log-error/color-danger; `warning` → log-warn/color-warning; `success` → color-success; `info` → color-info; `surface-glass` → surface-secondary; `overrides` всех 22 токенов сразу.
- `themeDerive` профили: все шесть баз; neon/matte glow; carbon ring; alpha-таблицы; `primary-dark`, `glow-secondary`, `glow-accent` не выводятся; untouched base values не переопределяются; вывод детерминирован при повторном запуске и не зависит от `resolvedVars` на входе.
- storage: сохранение/загрузка только source, отсутствие `resolvedVars`, битый JSON, неизвестная схема, quota error, повреждённый слот при `customThemeEnabled=true`, сохранение слота при отключении.
- bootstrap: тот же результат, что `resolveCustomTheme`, для всех баз и набора overrides; битые данные/отключённый слот/LG не применяют custom; проверка `data-theme`, `data-custom-theme` и только разрешённых inline-свойств.
- import/export: канонический round-trip; отказ при `resolvedVars` и лишних полях; неизвестная версия; лимит размера; ошибка не меняет текущий слот; замена только после подтверждения; preview не пишет в storage.
- `themeContrast`: alpha-композиция surface над bg; 4.5:1/3:1; автоконтраст `primary-contrast`; отсутствие ложного прохождения для полупрозрачных фонов.

## 7. Критерии готовности

- Ровно один слот пользовательской темы; списка и библиотеки нет.
- Встроенные темы не изменились визуально без согласованного решения.
- 22 seed-токена редактируются; 78 токенов и расширенный конструктор не входят в MVP.
- Сохраняемый и экспортируемый объект содержит только `schema`, `base`, `appearance`, `overrides`; `resolvedVars` нигде не персистится и не принимается.
- Применяются только переменные из закрытого allowlist 3.3; произвольный CSS и неизвестные ключи невозможны.
- Alpha разрешена только у шести surface-токенов; остальные токены непрозрачны.
- Производные вычисляются из изменённых seed-токенов; неизменённые значения базы не переопределяются.
- Custom-тема применяется без перезапуска и сохраняется после перезапуска.
- «Сбросить к базовой» и «Отключить» работают по отдельности.
- Liquid Glass и custom-темы не смешиваются; после отключения LG тема восстанавливается, снимаются только theme-owned inline-свойства.
- Нет вспышки темы при старте; bootstrap применяет те же правила, что и runtime, без ослабления CSP.
- Критически низкий контраст не применяется молча; полупрозрачные поверхности проверяются с alpha-композицией.
- Импорт не может выполнить CSS/JS-инъекцию; битый импорт не меняет текущую тему.
- Все строки локализованы; русский текст на «вы».
- `npx tsc --noEmit`, `npm test`, `cargo fmt --all -- --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test` зелёные.
- Визуальный аудит нормализованных производных выполнен на всех шести базах; расхождения с ручными эффектами зафиксированы.
- Документация обновлена, если фактическая схема отличается.

## 8. Риски и открытые вопросы

| Риск | Влияние | Смягчение |
|---|---|---|
| Захардкоженные цвета вне переменных | Тема выглядит неполной | Аудит этапа 0, постепенный рефакторинг |
| Нормализованные производные не совпадают с ручными эффектами | Тема на `ember`/`phosphor`/`carbon` выглядит иначе, чем база | Визуальный аудит, явные профили, не arbitrary CSS |
| 19 `!important` | Кастомные значения не применяются | Проверить и заменить точечно |
| Плохой контраст | Низкая доступность | WCAG-проверки, alpha-композиция, блокировка критических пар |
| Светлая тема ломает нативные контролы | Некорректный UI | MVP только dark; light — отдельный этап |
| Потеря единственной темы при очистке WebView | Пользователь теряет работу | Экспорт, предупреждение, позднее зеркало |
| Расхождение bootstrap и store | Вспышка/неверная тема | Общий валидатор, если CSP позволяет; иначе inline + тест эквивалентности |
| CSS-инъекция через импорт | Компрометация UI | Закрытый allowlist, HEX/RGB-парсер, фиксированные шаблоны |
| Импорт затирает текущую тему | Потеря настроек | Валидация до записи, подтверждение, запись только после успеха |
| Строгий импорт отклоняет чужие темы с лишними полями/HSL | Неудобная совместимость | Понятная ошибка; расширение формата отдельной версией схемы |
| Тема ломает Liquid Glass | Смешение режимов | Снимать только `appliedCustomVars` при LG |
| `surface-secondary` на базах без переменной | Отдельные компоненты не видят custom surface | Алиас выводится при изменении `surface-glass`; иначе остаётся fallback |
| Слишком много токенов | Сложный UI | MVP 22 seed-токена, advanced позже |

### Открытые вопросы

На уровне MVP открытых **продуктовых** вопросов нет: одна тема, 22 токена, импорт/экспорт, сброс, отключение и Liquid Glass зафиксированы. Библиотека тем, все 78 переменных, светлые темы, фоновые изображения и тонировка Liquid Glass вынесены на следующие этапы.

**Технические вопросы, требующие проверки:**

1. Достаточно ли нормализованных формул `primary-light`, gradients, glow и semantic tints для визуально приемлемого результата на всех шести базах, или нужны дополнительные явные параметры профилей.
2. Оставлять ли `log-*`/`banner-*`/`danger-*` производными от `error`/`warning` или сохранять ручные тона базы; текущий контракт выбирает производные с alpha-профилем.
3. Можно ли вынести bootstrap-валидатор в синхронный общий модуль без изменения Vite/Tauri CSP; до подтверждения используется inline-эквивалент.
4. Нужна ли поддержка HSL при импорте для совместимости с темами сторонних лаунчеров; текущий MVP принимает только HEX/RGB/RGBA.
5. Нужно ли выводить `--surface-secondary` для всех баз, а не только при изменении `surface-glass`; это влияет на fallback в `SkinPreview`.
6. Требуется ли точное пиксельное совпадение производных с ручными значениями; если да, это отдельный этап профилей, а не расширение произвольного CSS.

## 9. Сложность и оценка

- **MVP:** M, 3–5 рабочих дней после аудита.
- **Этап 2 (библиотека + полный редактор):** M/L, 5–8 дней.
- **Этап 3 (светлые темы, фоны, LG-тонировка):** L, 5–10 дней; каждое расширение требует отдельного аудита.
- **Основная сложность:** не UI, а целостность 78 токенов, захардкоженные цвета, контраст, первый кадр и защита от CSS-инъекций.
